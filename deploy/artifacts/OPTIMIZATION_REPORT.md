# Zero-cost concurrency rollout — 14 November 2026

## Deployed changes

- Added SQLite history index `(user_id, created DESC)`, due-account index and due-delivery index. Production query plan now uses `events_user_created`; no full history scan or temporary sort.
- One worker process now runs two polling threads with independent per-student SLCM sessions. Existing database claims, retry/backoff, pause controls and persisted schedules remain in place. No unbounded in-memory job queue.
- Push delivery runs in the worker's main thread, independently of both portal polling threads; existing delivery retries and expired-subscription cleanup remain.
- Each SLCM session has a total 120-second network deadline. Individual requests use at most 20 seconds or the remaining budget. This keeps checks below the 180-second account lease and preserves previous snapshots on failure.
- Successful and failed old polls cannot overwrite account state after reconnect/disconnect. Snapshot/outbox persistence and successful account updates commit together.
- Visible dashboards refresh 60–75 seconds after completion, with randomized timing. Hidden tabs pause; returning tabs resume after 0–3 seconds. Overlapping dashboard requests share the same promise. Manual refresh avoids a second redundant read.
- Kept existing VPS, Vercel, SQLite and installed dependencies. Other applications stayed running: Docker hosts an active Telegram service, and the portfolio telemetry agent is in use.

## Load test

Same dataset as baseline: 1,000 disposable users, six courses and 30 events each (30,000 history events). Synthetic accounts paused; no portal credentials or push subscriptions. Test requests validated the synthetic account identity. No live SLCM traffic was generated by fixtures.

External generator: operator's Windows connection. HTTPX per-operation timeout: 5 seconds. Warm connection ramps stop above 2 seconds p95 or 1% errors.

| External → direct API | 10 | 15s | 83ms | 117ms | 0 / 150 |

| External → direct API | 50 | 15s | 400ms | 2,021ms | 0 / 750 |

| VPS → local API | 100 | 15s | 157ms | 237ms | 0 / 1,500 |
| VPS → Vercel app → VPS API | 10 | 60s | 60ms | 113ms | 0 / 600 |

The 100 req/s external app test completed at 75.5 req/s including drain, with 14 read timeouts and one connect timeout. It is outside the smooth operating range. One initial external app warm-up also had five read timeouts out of 50 requests; the later warm-up passed. These failures were not discarded when assessing reliability.

Compared with the earlier app-path 50 req/s burst, observed p95 improved from 1,991ms to 624ms. External results remain variable; direct-API tails also varied. Successful loopback and VPS-origin app tests show that the server can serve substantially more than the proposed dashboard request budget. They do not prove which external route or proxy component caused the intermittent timeouts.

With 400 continuously visible dashboards, the new average 67.5-second refresh cadence generates roughly **5.9 dashboard requests/second**, plus initial/manual/action reads. Synchronized arrivals and sign-in spikes are different workloads. This test supports the lower request budget; it does not certify 400 live monitored students or guarantee every external request completes within five seconds.

## Remaining limits

No mass live-SLCM test, mass push fan-out, signup/login burst test, synchronized 400-client test or long soak was performed. Two concurrent portal checks do not mean all students finish refreshing simultaneously. Actual portal check duration and SLCM throttling determine queue capacity. Intermittent external 5-second timeouts remain unresolved. No paid infrastructure, new dependencies, Redis or PostgreSQL migration was introduced.
